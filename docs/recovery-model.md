# 收据丢了，能再做一次吗？

两台机器约好写一条记录。接收方写完了，回信在路上丢了。发送方看到的超时，与请求根本没到达时一模一样。这时原样重发一次，就可能得到两条记录。同样的推理适用于外部写入、任务提交和扣款。

模型追踪一个逻辑操作，输入和操作身份固定。每次尝试消耗一份预算。调用方保留首次错误的身份，接收方记录实际已生效次数。这两个数各有来源。暂时故障是否消退、资源是否够、是否仍在期限内，由真实调用者判断。永久错误转交修复。局部写入、仍在执行和结果无法查明，都需要先核对；在取得合同规定的证据前保持未知。

重放有两条依据。服务若承诺对同一个键和输入原子去重，可以在其保证有效的时间内重用原键。否则，权威读取必须能证明旧请求已结束并且没有生效。刚查到一张空表还不够，旧请求可能正在另一台机器排队。成功回执和权威确认都必须指向同一项操作。

用现有的 Z3 运行下列文件。前两项检查在任意非负整数预算下验证初始状态和每一步是否保持不变量。后两项给出真实可达的短路径，再故意绕过重放限制。[模型源码](examples/recovery.smt2)

```sh
z3 docs/examples/recovery.smt2
```

| 检查 | 预期 | 意义 |
| --- | --- | --- |
| 初始状态存在反例吗 | unsat | 还没开始时，预算完整，生效次数是零 |
| 合法一步能破坏约束吗 | unsat | 生效至多一次，确认成功对应一次生效，尝试消耗预算，首错保留 |
| 回信丢失后能正常结束吗 | sat | 查到写入已成功，无须再次写入 |
| 绕过限制会怎样 | sat | 同一非幂等操作实际写入两次 |

预算限制尝试次数。系统能否恢复，还取决于内存是否可用、网络是否恢复、执行者是否得到调度。真实程序需要验证操作身份、错误原件、去重语义或旧请求终结的证据。一个传输库提供 retry 开关，本身无法回答这些问题。

## 编译失败、磁盘满、断网，各怎么办？

十份内存里别的任务正在用五份，又来了一个需要七份的编译。原样重跑，仍旧差两份。等一项工作结束，实测有七份可用，再试就有了理由。操作系统杀了一个进程，先核实际退出和内存记录；只看退出码还分不清是内存用尽还是有人取消。

固定输入的读取被临时断网打断，可以在原截止时间和次数预算内退避重试。磁盘满时，先按宿主政策回收到期且无使用方的输出，核剩余空间，再回到原写入。断言稳定失败，追到输入或程序的责任处修复。原因未知，保留原错和现场，先诊断。一次操作仍未查清，只等待依赖它的工作。

第二个模型让求解器枚举故障原因、已观察到的副作用、资源是否恢复、剩余尝试数、有效期限和取消。它给出下一步建议。把「结果未知」误填成「确认未生效」，模型也会拿到错误的事实；调用方必须从实际任务核对这些输入。[日常开发故障模型](examples/development-failures.smt2)

```sh
z3 docs/examples/development-failures.smt2
```

第一问寻找不安全的处置，预期 `unsat`。后三问都是 `sat`。机器能找到安全重试、先释放资源再重试、确定性故障转交修复的输入。两个互相独立的操作可分别等待和继续。最后把策略换成「有余额就重试」，十份内存的例子立即给出反例。模型只给建议；程序实际如何保留错误、何时退避、调度器何时给 CPU，仍须原始运行验证。
